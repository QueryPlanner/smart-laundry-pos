## R1 — Preserve existing administrator login during migration (foundation)

counter.rs bootstrap checks only counter_accounts. Migration creates that table empty even when local_users has an existing admin. setup_admin then accepts an unauthenticated new PIN and overwrites the existing local_users credential. This both loses the user's existing login and permits taking over an upgraded installation.

Required: migrate the existing account/credential scheme without needing the plaintext PIN; verify/upgrade its hash on the first legitimate login. Setup is available only for a genuinely unconfigured database. Restore of v1 must behave consistently.

Done: isolated v1 database with a known admin upgrades, bootstrap reports setupRequired=false, original PIN works, wrong PIN fails, setup cannot overwrite it, and records/history remain intact.

## R2 — Respect staged-restore write blocking (foundation)

New counter mutations use writer_pool directly and bypass local_batch's restore_pending guard. After staging a restore, counter saves, rates, staff, matches, payment and print-state writes can still occur and be discarded on restart.

Required: apply a shared native write boundary to every counter mutation, coordinated with the existing restore lock. Preserve safe reads. Do not solve this only with a disabled screen button. Avoid bypasses in recovery and dispatch.

Done: stage a valid restore in an isolated fixture, attempt representative/all counter mutations and assert rejection with unchanged rows/jobs/money; safe reads remain usable and reopen applies restore correctly.

## R3 — Reopen earlier orders and complete the staff workflow (foundation + UI)

The only reachable order is the in-memory saved state in CounterApp. There is no staff order list/search, load-saved-order command, normal status change or later payment flow. Restart/lock/newer order prevents retrieving an earlier customer's tags or packing/pickup. Existing admin workspace is not a substitute for staff operations.

Required: add authorized, typed search/list and load APIs by bill number/customer phone, with pagination/bounds; a staff Orders / Pickup screen that works after remount; permitted processing/ready/collection actions and later payment recording. Full collection must be checked natively against matched pieces and valid order status; no scanner dependency. Existing legacy orders remain accessible without inventing physical counts. Use idempotency for payment submissions.

Done: create two fixture orders, remount/restart/login as staff, find the first by bill/phone, reopen pieces/jobs, record balance payment once, reject missing-piece collection, complete full collection after matching, and retain state after reopening. Staff cannot change rates/discounts/voids through these APIs.

## R4 — Print retry must actually dispatch; pending jobs need recovery (foundation + UI)

CounterApp doRetry calls retryPrintJob then refreshes. Native retry_job only changes failed/uncertain to pending; nothing submits it. PrintProgress has no dispatch action for pending jobs, so a save that failed because profiles were missing remains stuck. After restart there is no recovery view.

Required: wire bounded dispatch after retry, add an explicit resume action for pending output and a persisted queue view reachable after remount. Maintain independent destinations and uncertain-output confirmation. A failed Canon job must not reprint an already submitted TSC batch. Expose jobs with enough order metadata for actionable recovery.

Done: tests traverse real queue transitions with an injected fake spool adapter (no paper): failed -> retry -> submitted; missing configuration -> pending -> configure -> resume; remount -> pending visible; uncertain requires explicit confirmation; repeated click cannot create duplicate dispatches.

## R5 — Quote acceptance and idempotent saves (foundation + UI)

save_order recomputes a new quote at save time and compares rates only against that newly computed quote. It never checks the quote the operator reviewed. A price change while an order is open can silently charge a different amount. Idempotent retry checks happen after live quote/rate validation, so a previously saved request can fail once a rate changes. Reusing a key with a changed draft silently returns a different saved request.

Required: bind save to the reviewed quote/version/amount (native resolves real prices). Reject changed rates with a refreshed quote and explicit review. Look up already committed identical submissions before live rate validation; reject reuse for a different payload. Ensure UI does not save using a stale quote during debounce or after meaningful draft changes.

Done: quote at rate A, admin changes to B, save with old quote creates no order and requires review; retry a committed identical request after rate deactivation returns the original order without new payments/pieces/jobs; changed payload with same key rejects. Include draft edits during a pending quote and IST midnight handling.

## R6 — Selected-tag reprints must preserve original position/total (foundation + printing)

counter.rs reprint_output renumbers selected saved tags 1..selection length and changes total to selection length. Thus cloth 3/4 becomes 1/1 on a replacement tag. printing.rs and printDocuments.ts validate only complete sequential batches and therefore motivated the incorrect renumbering.

Required: preserve original saved piece ID, position and whole-order total on all reprints. Validators accept a unique subset of valid positive positions sharing the original total, without asserting total equals print-batch length. Selected pieces must still belong to the order.

Done: from four garments reprint only piece 3; payload/rendered content says 3/4 with identical ID, one tag request, no other document; reprint pieces 1 and 4 remains 1/4 and 4/4.

## R7 — Windows enumeration buffer handling is unsafe (printing)

printing.rs printer_entries discards EnumPrintersW's returned record count. list and driver_for interpret buffer.len()/size_of(PRINTER_INFO_2W) records, although the buffer also contains pointed-to strings. This reads strings as extra structs and may dereference invalid pointers.

Required: keep returned count; use correctly aligned storage and bounds checks; parse exactly that many entries while backing storage remains alive. Handle buffer resizing/errors and zero printers safely. Use official Windows API contracts. CreateDCW documentation recommends a null driver parameter for printing; avoid unnecessary unsafe repeated driver lookup if not needed.

Sources: https://learn.microsoft.com/en-us/windows/win32/printdocs/enumprinters and https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdcw

Done: Windows code is compile-checked if possible; Windows-target tests cover zero entries and buffers containing trailing string data; only actual returned queues are accessed. Report Windows execution honestly as pending if runner unavailable. No additional physical printing/layout work requested.

## R8 — New-order/session state and payment validation (UI + foundation)

Saving clears lines/payment but retains the previous customer. Lock also retains saved order, drafts, jobs and matching/reprint selections. On next login state can leak into a new customer's order. Negative payment input is allowed by the click handler because this is not a validated form; it is silently dropped rather than rejected. Counter quote errors also remain visible after a later successful quote.

Required: explicit new-order reset for customer/service(default Wash+Iron)/payment/quote/selections, while saved orders remain retrievable through R3. Clear account-specific transient state on native lock. Validate payment as finite nonnegative integer paise at both boundaries; either reject overpayment before save or consistently represent change/credit without generating a negative bill balance. Clear obsolete quote errors after successful validation.

Done: consecutive customers cannot inherit names/phones/services; lock/login starts clean; invalid/negative/nonfinite payment cannot save; errors recover cleanly.

## R10 — Matching identity/history and collection (foundation + UI)

match_pieces persists matches cumulatively and never clears them, while UI checkboxes appear to describe the current complete set. Previously matched pieces can be unchecked, submitted, and still count as matched. Duplicate detection only considers duplicates in one input batch. Packing and pickup use the same permanent flag, so an earlier packing check alone can masquerade as pickup verification.

Required: define and implement explicit current check sessions or stage-specific matches; checkbox semantics must reflect persisted state. For a full checklist submission, missing/unchecked pieces cannot still count complete from an earlier submission. If entering piece IDs manually, resolve printed short IDs safely and catch wrong-order/duplicates. At minimum distinguish packing checks from collection verification and enforce complete collection natively.

Done: match all, remove one on a later check, and completion is false for that check; wrong IDs/duplicates are rejected or accurately reported; collection validation is not accidentally inherited from packing.
